# 通讯助手：公开推广前的产品评估

评估日期：2026-10-15。基线为 0.3.3（构建 12）的实际源码、现有安装包与本机验收记录；本轮增加 PKG 交付，不修改应用二进制、不重启正在运行的账号，也不重置 72 小时观察。

结论：核心功能已经具备实用基础，可以继续受控测试；当前还不适合作为面向普通用户的正式产品推广。优先完成正式 API、签名公证、首次使用与升级恢复，再扩展规则数量。PKG 只是解决安装方式，不会消除这些阻塞。

## 事实、判断和未验证项

**已确认事实**

- 多账号、系统提醒、本地归档、搜索、备份和受控自动回复已有实现及测试证据。当前每账号只能绑定一个自动回复对象；支持全文/包含匹配和固定单行回复。
- 编号模式能关联同编号回执；固定回复缺少通用回执格式时只记录发送，不能确认对方已登记。
- 普通用户可以使用内置配置登录，但发布包目前使用官方 TEST ONLY 配置，正式自有 API 未完成。
- 现有应用为临时签名；本机未找到可用的 Developer ID Application 身份。PKG 安装器未签名、未公证。
- 账号会话与归档保存在本机；自定义 API Hash 使用钥匙串。数据库与备份并非应用级加密；目录权限限制不能等同于加密。
- 每次重启/恢复身份后，需要确认账号并重新开启自动回复。该行为能降低误发风险，也增加日常操作成本。
- 未看到应用内代理设置、版本检查或自动更新实现；网络连接失败主要提示用户检查网络或代理。
- 源码已公开，但原参考代码来源许可尚未核实；公开仓库不等于已授予开源许可。

**产品判断**

产品价值适合聚焦“多账号 Telegram 用户的本地消息助手”：把重要消息提醒、选择性留档和本人明确配置的固定回复做好。建议以这三项任务组织首次使用和宣传材料，让用户知道本机什么时候能处理、处理了什么、哪些结果仍待核实。

推广的主要成本将来自不同网络、系统版本、账号状态和安装升级，而不只是继续增加功能按钮。应先缩小支持范围并完成闭环，再扩展。

**尚未验证**

干净新 Mac 的完整下载、Gatekeeper 检查、管理员授权、安装、首次启动及卸载升级；干净 macOS 14 兼容性；完整 VoiceOver/键盘路径；不同网络及高频来信；新版完整 72 小时。当前本机运行结果不能替代这些条件。

## 本轮安装方式优化

会记本地项目 `package-installer.sh` 的可复用处理是：PKG 图形向导、固定安装到 `/Applications`、禁止跟随旧副本重定位、版本检查、升级替换应用、安装前要求退出原应用、完成后给出首次使用步骤。会记自身也仍是未完成签名公证的测试安装器。

通讯助手现在采用同样的交付方式：

1. 下载 `CommunicationsAssistant-0.3.3-macOS-arm64.pkg`。
2. 阅读安装与升级说明，按“继续 → 安装”操作；系统可能要求管理员验证。
3. 从“应用程序”打开通讯助手。应用和独立引擎随包交付，无需 Python、Docker 或终端。
4. 登录/确认账号，测试通知，选择需要的归档和回复规则。

安装器仅包含应用载荷，不包含登录、下载依赖、读取用户资料、修改账号设置、关闭安全保护或自动启动程序的脚本。最低系统版本取自实际应用元数据；当前为 Apple Silicon、声明最低 macOS 14，仍需旧系统实测。网站将 PKG 设为首选，DMG/ZIP 保留备用。

**本轮验证边界**：实际展开 PKG，核对应用内容与签名、固定安装位置、架构/系统限制、升级和退出元数据、安装选项；实机查看欢迎页、安装说明及标准安装确认页。未在当前工作 Mac 点击最终“安装”，避免打断现有自动回复和观察；未将新 Mac 完整安装标记为通过。应用包及原 v0.3.3 标签保持不变，安装交付脚本版本另记在发布元数据。

## P0：普通用户正式推广前必须完成

| 项目 | 当前缺口与影响 | 完成标准 |
| --- | --- | --- |
| 产品自己的 Telegram API | 官方测试 API 受服务端限制，不适合终端用户发行 | 团队控制的自有 API 完成申请和测试；普通用户只登录自己的 Telegram；高级设置保留自定义 API |
| 签名、公证与稳定身份 | 当前应用临时签名，PKG 未签名；下载拦截、重复钥匙串确认及来源信任仍未收口 | Developer ID Application 签应用及内嵌组件，Developer ID Installer 签 PKG；完成公证、装订和联网/离线 Gatekeeper 验证；升级身份保持一致，应用标识变更需显式迁移钥匙串与偏好设置 |
| 来源和许可 | 参考代码缺少可验证的原仓库与许可，项目尚未确定自身许可 | 补齐来源、权限及第三方清单，明确产品自身许可；无法确认的参考代码重新实现或移出交付链 |
| 安装与兼容性闭环 | PKG 向导不代表干净机器可安装；最低系统版本只有声明 | 在支持矩阵的干净 Mac 验证下载、首次安装、同版本修复、升级、取消、失败及资料保留；只宣传真正验收过的系统范围 |
| 用户可理解的数据说明与支持渠道 | 当前 SECURITY 更偏维护者，尚缺完整用户入口 | 明示本机保存内容、Telegram 网络交互、默认不归档、备份未加密、会话退出及删除方式；确定实际反馈与私密安全报告渠道，不让用户把凭据/聊天贴到公开 Issue |

Telegram 官方明确说明示例 API ID 不适合面向终端用户发布，可能触发 `API_ID_PUBLISHED_FLOOD`；API 条款也要求使用自己的 API ID、清楚说明第三方身份及获得用户授权。这是实际发行条件，无法通过换成 PKG 解决。[官方 API 申请说明](https://core.telegram.org/api/obtaining_api_id)、[API 条款](https://core.telegram.org/api/terms)。

Apple 说明 App Store 外的应用和安装器会受到开发者 ID 与公证检查。应完善签名交付，不能把让用户关闭系统保护当成正常安装步骤。[Apple 官方说明](https://support.apple.com/zh-cn/102445)。

## P1：形成能长期使用的工具体验

### 1. 首次使用和运行自检

把账号确认、网络连接、通知权限、归档选择、规则预览串成可跳过、可返回的准备过程；已有用户复用配置，只补缺项。概览明确列出“正常运行 / 仅提醒 / 发送已暂停 / 登录待确认 / 网络不可用”，每项有对应处理按钮。

权限在使用对应功能时请求。先完成第一条通知和第一条合成规则预览，再引导后台运行；不能要求用户在一大页高级设置中自行排错。移入应用程序和已运行副本的识别也需要清楚提示，避免开着下载目录中的旧版又打开安装后的新版。

验收：新用户能独立完成安装、登录与通知测试；拒绝通知权限后仍可使用其他模块，并能从自检页返回系统设置。

### 2. 网络诊断和恢复

先提供可操作的连接诊断，区分网络不可达、Telegram 限流、登录失效和引擎故障；不显示凭据和消息正文。确认受众需要后，再加入明确的代理类型、连接测试及密码安全保存，避免把系统代理“看起来开启”当成 MTProto 已能使用。

验收：直连、受支持的代理、断网重连、睡眠唤醒、限流等待都有可解释状态；等待期间不把发送记录标为成功，不补发过期提示。

### 3. 每账号多对象与多规则

从单个目标字段升级为规则列表：目标、匹配条件、回复、有效期、允许时段、启用状态。先保留现有全文/包含和编号关键词能力；每条规则可独立预览与暂停。

同一目标有多条匹配时，应预先提示冲突，并明确只执行一条的优先级。来源消息的发送去重必须覆盖规则之间，不能因为换规则就再次发送同一条提示。规则需要稳定标识和带版本的数据迁移，旧配置自动成为第一条规则。

验收：同账号两个目标独立工作；同目标重叠规则只发送一次；切换账号、编辑规则、导入模板均不交叉发送。

### 4. 回复和回执形成闭环

执行记录应明确区分“待处理、已跳过、发送中、已发送、回执确认、结果未知”，提供原因和原消息定位。扩展自定义回执前，先确定可关联的编号/消息关系；没有可靠关联时继续保留“登记未核实”，不能把任何一条“成功”文本当成当前任务已完成。

验收：延迟回执、重复回执、错误编号、多个同时待回执任务，以及没有回执的固定回复均给出正确状态。结果未知时不自动重试。

### 5. 重启、升级与启用意图

保留目前“不默默恢复发送”的保护。增加清楚的恢复页，让用户核对账号、规则变更和上次已启用状态，一次确认恢复选中的规则。正常升级、用户手动退出与异常崩溃分开呈现；不要在崩溃恢复时跳过确认重新发送。

设置中先增加“检查版本、查看更新、下载并按向导升级”的小闭环；正式签名完成后再评估受校验的自动更新，减少维护自研特权安装服务的成本。

验收：升级不丢会话、归档或账本；每条原先启用的规则都有明确恢复状态；用户关闭的规则保持关闭；旧提示不补发。

### 6. 完整的账号和数据管理

集中显示所有账号、连接状态和规则状态；明确“退出登录”“移除入口”“删除本地资料”各自影响。当前移除入口保留磁盘数据，但旧归档不会自动合并到新入口，普通用户需要可发现的离线资料恢复入口。

规则支持单独导入导出，导入先预览目标及变更，不携带凭据，默认关闭发送。备份增加可选加密与恢复演练；会话凭据继续与普通业务备份分开。

验收：误移除可恢复保留的资料；恢复只作用于对应身份；关闭应用、删除应用及删除本地资料的区别清楚。

### 7. 公开支持和可访问性

在应用与网站提供统一版本、使用说明、已知问题和反馈入口。诊断导出前可预览，默认仅包含版本、匿名错误和状态计数；不默认上传遥测。完成键盘焦点、VoiceOver、长名称、小窗口和错误提示的验收。

## P2：有真实需求后再增加

Intel 版本、二维码登录、更多语言和提示音、收藏与更多导出格式，可以由测试反馈排序。云端全天运行、团队协作、收费、AI 回复和任意脚本会显著增加运行、隐私及维护范围，暂不作为首轮推广的必要条件。

## 建议的推进顺序

| 阶段 | 交付目标 | 放行证据 |
| --- | --- | --- |
| 当前测试版 | PKG 交付、安装说明、现有功能继续验收 | 安装器结构与向导检查；现有自动回复继续运行；新版 72 小时单独核对 |
| 公开测试候选 | 正式 API、签名公证、来源说明；准备向导、诊断和更新闭环 | 干净机器无需终端或关闭保护即可安装；普通用户无需申请 API；独立测试者能自行完成首次使用和升级 |
| 可推广版本 | 多规则、回执/未知状态、恢复与数据管理稳定 | 重叠规则不重复发，错误身份不发，过期提示不发；异常可解释，反馈可定位；支持矩阵和长期观察有独立记录 |

不将“72 小时到了”“CI 通过”“安装器打开了”或“消息已发送”单独当作完整产品放行。推广前应能逐项回答：用户能否独立安装、知道当前状态、恢复中断、看懂实际结果，以及安全保留和移除自己的资料。
